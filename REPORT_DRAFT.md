# Secure Personal Ebook Tracker — report draft

## Unsecured baseline

The first implementation is a deliberately vulnerable, local-only ebook tracker built with React, Flask and SQLite. Users can list, search, add, edit and delete books, including private reading notes. Two ordinary demonstration accounts, `doon` and `otherdoon`, make it possible to test whether one reader's records remain private. Figure 1 shows the baseline data flow; the screenshots catalogued in [SCREENSHOTS.md](SCREENSHOTS.md) provide observed behaviour. This baseline is a comparison point for the later secured implementation, not a deployable application.

The sign-in form accepts a known username without a password. The server returns a user record but creates no authenticated session. Consequently, the browser's displayed identity does not establish who is making subsequent API requests. Changing `/users/1/dashboard` to `/users/2/dashboard` while still shown as Doon exposes Otherdoon's library and private notes (screenshots `20261013110122` and `20261013110140`). Similarly, `/admin` and `/api/admin/books` reveal all readers' records to a visitor who has not signed in (screenshots `20261013105830` and `20261013110457`). These observations demonstrate missing server-side authentication and resource-level authorization; hiding an admin link in the interface would not protect its endpoint.

The search endpoint also trusts client input. Its ordinary title-search path inserts the supplied text into a SQL string rather than binding it as a parameter, permitting SQL injection. For presentation, a separate path deliberately accepts complete client-supplied `SELECT` and `UPDATE` statements. Screenshot `20261013112042` shows an `UPDATE` entered through the search box and the application reporting three changed rows; Otherdoon's notes display the changed value. This screenshot demonstrates direct execution of client-supplied SQL and missing write authorization. It should **not** be labelled as proof of classic quote-breaking SQL injection, which is a distinct weakness in the ordinary search path.

Finally, the sign-in endpoint applies no attempt limit. Repeated requests for an unknown username continue to return HTTP 404 (screenshot `20261013112515`). Because this baseline has no passwords, this evidence concerns unrestricted invalid-username attempts, not password guessing. The later implementation should repeat these same access, query and login tests, showing both rejected malicious requests and successful legitimate operations.
