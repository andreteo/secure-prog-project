## Is there a cybersecurity “bible”?

There is no single universally authoritative book covering secure coding, web application security, threat modelling and deployment. **Ross Anderson's _Security Engineering_ (3rd edn, 2020)** is the closest broad system-security textbook here. The [author provides the complete edition legally](https://www.cl.cam.ac.uk/archive/rja14/book.html); chapters on access control, protocols, network defence, secure development and assurance are relevant. Its value is a system-level argument about security boundaries and failure modes, not a ready-made Flask checklist. For this report, pair it with **Gary McGraw's _Software Security: Building Security In_ (2006)** for security activities across development and **Adam Shostack's _Threat Modeling: Designing for Security_ (2014)** for diagram-led analysis. [Saltzer and Schroeder's 1975 paper](https://web.mit.edu/Saltzer/www/publications/protection/index.html) is a classic primary source for complete mediation and least privilege. The report uses these books/paper for design reasoning and current NIST/OWASP sources for specific web controls.

| [Saltzer and Schroeder (1975)](https://web.mit.edu/Saltzer/www/publications/protection/index.html) | Complete mediation and least privilege | API checks ownership on each book route and admin role on the admin route | Hiding links or relying on unpredictable IDs is not mediation |
| [NIST SSDF v1.1 (2022)](https://doi.org/10.6028/NIST.SP.800-218) | Integrate security practices into any SDLC; prepare, protect, produce and respond | Requirements, design, coding, tests and limitations are documented together | SSDF gives outcomes; it does not supply a turnkey web-app implementation |
| [OWASP ASVS 5.0.0 (2025)](https://owasp.org/projects/asvs) | A versioned set of web-application verification requirements | Use as a checklist for authentication, access control, input and session tests | Do not claim ASVS compliance without checking every applicable requirement |
| [OWASP WSTG v4.2 (2020)](https://wstg.owasp.org/v4.2/) | Repeatable test cases for authorization, login, injection and transport | Match baseline attacks with secured requests and database-effect checks | WSTG is a testing guide; a few selected cases are not a comprehensive penetration test |

## Tools, evidence and citation discipline

The project's disposable SQLite test suite is better evidence for ownership and data integrity than a scanner alert. [ZAP's own documentation](https://www.zaproxy.org/docs/desktop/start/features/scanpolicy/) says automated active scans cannot find logical broken-access-control vulnerabilities, so they require manual tests. [PyPA's `pip-audit`](https://github.com/pypa/pip-audit) can check installed Python packages or requirements against known vulnerability advisories; it does not analyze application code. Neither tool has been run for the results currently stated in the draft report. If run later, record command, version, findings and fixes rather than implying a clean scan proves security.

The report bibliography uses **Harvard author–date** because the user requested it. The supplied assessment rubric repeatedly requires **APA 7**. This is a real marking risk, so switch to APA 7 for the final submission unless a current lecturer/module instruction overrides the old brief. The report's source list should use the exact edition and year cited, and OWASP undated pages need access dates because their contents can change. WSTG v4.2 has a dated [3 December 2020 release](https://wstg.owasp.org/downloads/), so cite **OWASP (2020)**, not `n.d.`. Cite NIST SP 800-63B-4's final [2025 publication](https://csrc.nist.gov/pubs/sp/800/63/B/4/final), not the earlier SP 800-63B version with a similar title.
